# 画布工程包导出（可选）

> 用途：当用户的生成平台是**节点画布工具**（把提示词、参考图、连线摆成工作流，再逐节点执行），且支持**导入工程包**（一个 zip）时，把第5站产出的 N 条视频提示词批量变成画布上的 N 个节点。
> **不做这一步也完全不影响第5站交付** —— 提示词文本本身就能直接粘。

---

## 一、三条分组铁律（比格式更重要）

1. **连续的镜头必须合并成「一个节点」一条过。**
   同一个场景 / 同一片光 / 同一身衣服、且动作或运镜能连续接上的镜头，拆成多个节点会**一致性崩**
   （人物长相、服装、光线、空间全都会漂）。反过来，**独立场景必须拆开**，不能硬塞进一个节点。
   → 输出前先问用户：**哪些镜头算一组？** 给出分组方案让用户确认或改。
2. **每个阶段要有自己的「构图约束」。** 一个节点里含多段时，逐段给该段的图像/描述做构图锚点，
   并逐段写明画面效果，否则模型会把几段揉成一段。
3. **生成顺序 ≠ 剪辑顺序。** 分组按「拍摄单元」归，不按成片里的先后。**务必跟用户确认这一点**，
   否则会按剪辑顺序硬排，破坏上面的合并规则。

---

## 二、逐节点写提示词的规则

- **静帧不做「首帧」，只做「关键帧参考」。** 静帧是一个瞬间，视频要动；写「作为首帧」会锁死运镜。
  正确写法是「用于该段的画面构图、人物位置与画面效果，作为关键帧参考」。
- **提示词里禁止出现编号指代**（「镜03」「上一镜」「与第 2 镜同一束光」这类）。
  模型看不懂编号。要引用就把**内容写全**（那条街什么材质、什么光、什么角度），
  或把被引用的图/提示词一并作为参考素材给进去。
- **音效**：若用户要同期声，就在【声音】里**写明音效内容**，并在节点配置里**把音效开关打开**；
  不要 BGM 就明确写「没有音乐」。
- **时长**：每个节点写清楚秒数。**先查目标平台的时长合法范围**（画布工具通常是个滑杆区间，
  如 4–15 秒整数），超出范围会被拒。

---

## 三、工程包的技术要点（踩过的坑，按顺序）

1. **先拿到一个「该平台自己导出的」工程包当样本**，把它的结构、字段、枚举全部解析出来。
   自己凭空猜字段一定失败 —— 样本是唯一权威。
2. 常见结构：`manifest.json`（素材清单）+ `project.json`（节点与连线）+
   `assets/<id>.<ext>`（图片实体）。
   - 节点记录通常形如 `{id, type, data(JSON 字符串), created_at …}`
   - 连线记录形如 `{sourceNodeId, sourcePortId, targetNodeId, targetPortId, style, color}`
   - 画布是 **tldraw** 类引擎时，`project.json` 里**视觉与逻辑是两套**：
     `content.shapes`（每个节点一份 shape，带 x/y/w/h/props）和 `workflowNodes`（逻辑），
     **两套都要生成，且 id 要对得上**；还得有 `content.schema`（可直接从样本原样复制）。
3. ⚠️ **zip 条目必须「不压缩」（STORE）**。这类工具常自己手写 zip 解析器逐条读 local header，
   只认 STORE 方式；用默认的 DEFLATE 压缩会直接导入失败。
   生成时用 `zipfile.ZipFile(p, 'w', zipfile.ZIP_STORED)`，并确认 `flag_bits == 0`。
4. ⚠️ **枚举字段必须逐字对上**。节点的状态、类型、连线样式等往往是固定枚举
   （例如状态只接受 `idle/queued/running/completed/error`）。自己编一个词就整包失败。
   **枚举要从样本里抄，不要自己造。**
5. ⚠️ **输出结构要「按能力名分键」**。同一份节点数据里，输出字段通常是
   `outputs.<能力名> = {...}`（生图是 `outputs.conceptArt`、图片输入是 `outputs.imageInput`、
   视频是 `outputs.seedance`）。写成空对象会让节点变成**点不动的空壳**。
6. **图片可以内嵌**：节点引用本地图片时常有专门协议（如 `project-asset://<素材id>`），
   配合素材清单登记，就不必先把图传到云端。
7. ⚠️ **参考图的宽高比有上限**（不少平台限制 **≤ 2.5**）。宽幅全景素材最容易踩 ——
   场景图/环境图常在 2.7–3.4 之间。
   → **打包前把每张被引用的图都量一遍**（不只是分镜帧，**角色图、场景资产也要量**）。
   → 超标的处理：**保留高度、居中裁切宽度**到上限以内（留一点余量，例如裁到 2.48）；
     **原图先备份**再替换。不要用「补边」的办法 —— 加出来的区域是假的，模型会把它当画面内容读。
   → 定稿帧、线稿这类 16:9 的图通常没问题，**重点查场景资产**。

## 四、排错

这类工具报错常常只有一句「无法导入 / 加载失败」，**真正原因在它的日志里**。
日志一般在用户数据目录下（如 `%APPDATA%\<app>\logs\app\main-<日期>.log`）。
先读日志定位到具体函数，再去**解包 App 本体**（Electron 应用在 `resources/app.asar`，
用 Python 按 asar 头解析：JSON 头从第 16 字节开始、长度在 offset 12，数据体在头之后对齐 4 字节）
把校验代码读出来 —— 校验器会明确告诉你哪个字段不合法。**一次只改一处、让用户重试**，收敛很快。

---

## 五、输出

一个可供用户导入的工程包 zip + 一句「每个节点对应哪几镜、时长多少、模型要选什么」的说明。
